# Клиентская криптография v1

Backend совместим с текущим `messenger-frontend/src/crypto/envelope.js`.
Клиент использует AES-256-GCM: случайный ключ 32 байта на диалог, новый
IV 12 случайных байт при каждом шифровании и тег 128 бит в конце `ct`.
Сервер хранит и маршрутизирует только шифротекст; ключ ему не передаётся.

AAD — UTF-8 без BOM от следующего массива JSON без пробелов:

```js
const aad = new TextEncoder().encode(JSON.stringify([
  1, dialogId, senderId, id, sentAt
]));
```

`dialogId` и `id` — UUID в стандартной форме с дефисами и нижним регистром.
`senderId` — читаемый **публичный ID** пользователя (`session.user.publicId`
текущего веб-клиента), с сохранением регистра. Backend получает его по
аутентифицированной сессии, а не из тела запроса. Внутренний UUID пользователя
не участвует в AAD и не возвращается как `senderId` сообщения.

`sentAt` — целое неотрицательное число миллисекунд Unix (`Date.now()`),
например `1794916800000`, без кавычек. ISO-строки, дробные числа и значения
за пределами представимого сервером времени отклоняются. В БД время остаётся
UTC, но REST/SignalR всегда возвращают то же числовое значение миллисекунд.

Пакет отправки: `{v,id,sentAt,iv,ct}`. `iv` и `ct` — канонический Base64url
без `=` (алфавит `A-Z a-z 0-9 - _`). Для совместимости прежних API-тестов
сервер также принимает канонический standard Base64; ответы всегда Base64url.
Пробелы, некорректный padding и неканонические остаточные биты отклоняются.

Получатель использует `dialogId` и публичный `senderId` ответа вместе с
неизменённым пакетом для восстановления AAD. Проверка тега предшествует выводу
открытого текста. Изменение отправителя, ID, времени или ciphertext должно
приводить к ошибке расшифрования; непроверенные байты не отображаются.

[Публичный тестовый вектор](protocol-v1-vector.json) с фиксированными тестовыми
ключом и IV создан импортом **текущего** frontend `encryptMessage`. Он проверен
его же `decryptMessage`, а `FrontendContractTests` проверяет десериализацию
пакета сервером, канонический ответ и расшифрование с идентичным AAD.
Тестовые ключ и IV не используются в настоящих сообщениях.

Backend не реализует WebCrypto/IndexedDB, ручной обмен ключами или очистку
памяти браузера. Изменение AAD требует согласованной новой версии протокола;
формат текущего клиента сохраняется.
