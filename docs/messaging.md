# Сообщения и доставка — протокол v1

Все операции требуют действующей cookie-сессии. Посторонний получает 404,
как для несуществующего диалога. Сервер берёт senderId из сессии, а не из
JSON клиента. `GET /auth/me` возвращает также внутренний UUID `id`, необходимый
клиенту для AAD. UUID и ciphertext сообщения доступны только участникам.

## REST

`POST /dialogs/{dialogId}/messages`:

```json
{"v":1,"id":"33333333-3333-4333-8333-333333333333","sentAt":"2026-11-17T12:00:00.000Z","iv":"AAECAwQFBgcICQoL","ct":"BASE64_CIPHERTEXT_WITH_GCM_TAG"}
```

`v=1`, непустой UUID, UTC sentAt с точностью до миллисекунд, IV ровно 12 байт,
ct от 16 до 65536 байт, включая 16-байтный тег. Байты передаются в base64.
Сервер проверяет форму пакета; корректность AES-GCM проверяет клиент.

Новая отправка возвращает 201:

```json
{"message":{"dialogId":"...","senderId":"...","v":1,"id":"...","sentAt":"...","iv":"...","ct":"..."},"created":true,"deleted":false,"revision":1}
```

Идентичный повтор `(dialogId,id)` от того же отправителя возвращает 200,
`created=false` и не создаёт строки/событие заново. Другой отправитель или
изменённый пакет с тем же ID получает 409 `message_conflict`. Повтор после
удаления собственной копии возвращает `message=null, deleted=true` и не
восстанавливает переписку. Клиент должен повторять исходный пакет целиком:
повторное шифрование с новым IV требует нового message ID.

Две строки владельцев, квитанция отправки и увеличение ревизии записываются
в одной транзакции с блокировкой строки диалога. Минимальная квитанция хранит
ID диалога/сообщения/отправителя, SHA-256 отпечаток пакета и ревизию, без
шифротекста, IV и исходного времени. Она сохраняется после удаления, чтобы
задержавшийся retry не воссоздал удалённые строки. Это сохраняемые метаданные,
а не флаг скрытия рабочего сообщения.

`GET /dialogs/{dialogId}/messages?limit=50&before=<cursor>` возвращает
`{items,nextCursor,revision}`. limit: 1–100. Порядок: sentAt по убыванию,
затем client message UUID по убыванию. Курсор непрозрачен; передавайте его
без изменений. Конец истории: `nextCursor=null`. Страница содержит только
копии текущего владельца. Изменения во время пагинации требуют сверки ревизий.

`DELETE /dialogs/{dialogId}/messages/{id}` удаляет свою рабочую строку.
`?forEveryone=true` удаляет обе рабочие строки атомарно. Любой участник может
удалить у обоих. Повтор удаления возвращает 204. Отсутствие своей копии не
мешает участнику запросить удаление оставшейся копии у обоих.

Вложения удаляются каскадно. Пока другой владелец ссылается на зашифрованный
файл, файл остаётся. Последняя ссылка создаёт задание удаления в той же
транзакции. После commit сервер пытается удалить файл сразу; при временном
сбое фоновая уборка повторяет попытку каждые 30 секунд. Это обеспечивает
восстановление после падения между фиксацией БД и удалением файла. Рабочее
удаление не обещает очистку WAL, резервных копий или носителя.

`POST /dialogs/{dialogId}/messages/sync` с `{ids:[...]}` (до 500 непустых UUID)
возвращает `{missingIds:[...],revision}`: какие из переданных ID больше не
принадлежат текущему владельцу. Пустой список разрешён для чтения ревизии.

## SignalR

Hub: `/hubs/messages`. Гость получает 401 ещё при negotiate/подключении.
Нет публичного метода вступления в произвольную группу. Подключения сервер
привязывает к пользователю и cookie-сессии; сессия проверяется перед каждым
событием и вызовом hub. Отозванная/истёкшая сессия отключается при следующей
проверке и не получает новые сообщения. `Ping` позволяет проверить сессию.

- `MessageReceived`: `{message:<MessageResponse>,revision}` — обоим участникам.
- `MessageDeleted`: `{dialogId,id,forEveryone,revision}` — владельцу при удалении
  у себя, обоим участникам при общем удалении.

События отправляются после commit. Они могут прийти повторно, с задержкой или
не прийти при разрыве соединения; REST остаётся источником истины. Доставка
одним процессом соответствует Compose MVP; для нескольких API нужен общий
backplane и распределённое управление подключениями.

## Алгоритм восстановления клиентом

1. При потере связи пометить память устаревшей. После восстановления сначала
   подключиться к SignalR, дождаться успешного `Ping`, буферизовать события.
2. Сверить ВСЕ ID сообщений из памяти через sync порциями до 500; удалить
   missingIds из памяти и освободить связанные blob URL.
3. Получить историю, объединяя по message ID. Запомнить server revision.
4. Применить более новые буферизованные события. Ответы/события со старой
   ревизией не должны восстанавливать удалённое сообщение. При разрыве между
   ревизиями, различии ревизий порций sync/истории или конфликте выполнить
   сверку заново. Не считайте страницу или набор порций атомарным снимком.
5. После logout очистить расшифрованные сообщения и ключи в памяти клиента.

Это контракт backend. Фронтенд должен реализовать этот алгоритм; изменение
состояния открытой вкладки не выполняется сервером автоматически.
